# Orchestrator, schedules, run ledger

A job's **orchestrator** is just an action that emits the plan — `meta.orchestrate` (the job's `orchestratorAction`; the old `meta.plan-job` name survives only as a legacy id in `work-queue.ts` — the matching journal migration in `journal-store.ts` was retired once no `meta.plan-job.jsonl` remained on disk). The action catalog goes into its envelope so it can compose actions into a plan; no separate "playbook" primitive is needed.

**The catalog is scoped to its reader** (`buildActionCatalog` + `CatalogScope`, `src/work/envelope.ts`). It used to ship every action to everyone, which put a controller's internal rounds in front of the orchestrator as if they were plannable steps, and put each controller's roster in front of the other. Two slices now, and the scope argument is required so a new call site has to say which it is:

- **`plannable`** — what `meta.orchestrate` may emit as a job step. An action opts out with `outpost.plannable: false`, which marks it as reached some other way: a controller round (`code.implement`, `code.fix-ci`, …), a UI button (`meta.build-action`), a schedule (`meta.improve-actions`). The default is `true`, so a newly built action is visible to the planner without knowing the field exists — the failure mode of forgetting it is a visible extra entry, not a silently unplannable action.
- **`controller`** — what a step-orchestrator may rebind to or dispatch: its declared `outpost.roster` plus itself. An undeclared roster falls back to the whole catalog, because showing a controller *less* than it needs strands the step with no way to name what it wanted, while showing too much only costs tokens. `load()` rejects a roster naming an unknown action — that would be a rebind target the controller can never reach, failing mid-step after the work leading up to it.

Concretely: 27 entries / ~24k tokens unfiltered, versus 11 / ~4.7k for the orchestrator and 11 and 7 for the two controllers. `daemon.ts`'s separate catalog for the schedule builder stays unscoped on purpose — a schedule legitimately runs actions no job plan may emit. Pinned by `action-catalog-scope.test.ts`.

**Schedules** (`src/schedules/`, "routines" in the UI) fire work without a user asking. A `Trigger` is `cron` / `once` / `event` / `token-opportunistic` (fired by spare 5h/7d token headroom rather than a clock — see `headroom.ts` + `token-scheduler.ts`), `Guard[]` can veto a firing, and a `What` runs one of four things: a catalog `skill`, a free-text `prompt`, a `script` (no Claude session at all), or a `native` in-daemon handler (how the PR watchers are wired).

Every action round is recorded: `action-run-ledger.ts` observes the job queue and writes one `ActionRunRecord` per round, with an outcome (`accepted`/`revised`/`denied`/`merged`/`failed`/…), cost, and denial count. That feeds `scorecard.ts` (the Library's skill detail pane) and `improvement-pack.ts`, which picks the single action most worth improving and assembles its evidence for `meta.improve-actions`. This is why the journal-blocker entry in [gotchas.md](gotchas.md) matters — those entries are the qualitative half of that evidence.

**"Every round" did not include a controller's, and that silently exempted thirteen actions from ever being improved.** `roundOf` (`action-run-derive.ts`) bailed on any step that wasn't an `ActionStep`, so `code.reply-pr-comments`, `code.implement`, `code.fix-ci` and every other action reached only as a controller-bound round had **zero rows** in `action-runs.jsonl` — while `selectActionToImprove` elects on run counts and scores on run outcomes. The only door left was a recurring permission denial, which is why nine consecutive user skips of `code.reply-pr-comments`'s drafts moved nothing. A controller round is now derived too, keyed on **its bound action alone** — deliberately not on `roundsSpent`, because the two move at different mutations (`roundsSpent` increments when the controller reports a move, `boundAction` only when the next round launches), so a composite key opens a phantom row for the outgoing action every round. The cost is that consecutive rounds bound to the *same* action collapse into one row, which lands on the controller's own back-to-back decision turns and not on the sub-actions this exists for. A draft gate suffixes the key (`code.reply-pr-comments#draft`), so the gate's verdict patches the sub-action's row rather than whatever ran before it, and `attempt` counts recurrences of a binding on that step — which inflates `avgRevisions` for a controller with dozens of decision turns. Still uncovered: a **dispatch**, since the ledger keys an open run by `jobId:stepId` and sibling dispatches run concurrently under one stepId. Pinned by `action-run-derive.test.ts`.

`needsAttentionScore` (`improvement-pack.ts`) counts `denied` alongside `failed`/`revised` for the same reason: without it an action whose payload the user throws out *every single time* scores zero, which is exactly how those nine skips left `code.reply-pr-comments` bottom-ranked behind actions with ordinary denial counts.
